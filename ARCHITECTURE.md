# DevSpace — устройство и безопасность

## Два независимых слоя

- **Публичное портфолио** — разделы `#featured`, `#about`, контакты. Доступны посетителям без входа, данные берутся из проверенных ссылок на репозитории.
- **Истории проектов** — маршруты `#project/<slug>`, данные и рендер в `js/portfolio.js`; не требуют сборщика, не зависят от Firebase и открываются по прямым ссылкам. Иллюстрации сейчас концептуальные, а не игровые скриншоты.
- **Vercel-проекты** — вручную проверенная витрина четырёх проектов в `#web-projects`. Статус сборки `READY` не означает публичный доступ; текущие проекты используют Vercel SSO Protection, поэтому на карточках есть явное предупреждение. Приватные исходники не раскрываются ссылками.
- **GitHub metadata** — `js/github-metadata.js` запрашивает только шесть явно разрешённых публичных репозиториев. Дополнительный импорт репозиториев в мастерскую использует только публичный GitHub API без токена; устаревший PAT из `localStorage` удаляется при инициализации, токены больше не читаются и не отправляются. Поля `private` и `full_name` проверяются перед показом, нет токенов, кеш сессии живёт 30 минут. При сетевой ошибке сведения не выводятся, а основной сайт продолжает работать. Это сведения о последней отправке кода (`pushed_at`), а не обещание актуального статуса разработки.
- **Галереи** — `Skyward Tales` использует реальные скриншоты из `docs/screenshots/`, а блок `DM Workspace` — тестовые снимки интерфейса из `tests/screenshots.spec.ts-snapshots/`. Ссылки указывают на публичные файлы ветки `main` исходных репозиториев, без копирования закрытого содержимого. Изображения могут исчезнуть при переименовании файлов в источнике; основной текст при этом сохраняется.
- **Просмотр изображений** — `js/portfolio-gallery.js`, отдельное модальное окно, не использует старый `GalleryModule` трекера. Поддерживает клавиатуру, свайпы, оригинальные ссылки, восстановление фокуса; обычная ссылка продолжает работать при Ctrl/⌘-клике или отключённом JS.
- **Мастерская** — существующий трекер проектов, задач, заметок и достижений. Локальные правки хранятся в браузере (через `StorageService`). В интерфейсе доступны экспорт и импорт резервных копий.

## Известные ограничения

Раньше `AuthService` сравнивал введённую строку с ключом внутри публичного JavaScript. **Это не была безопасная авторизация.** Теперь интерфейс честно называет эту функцию локальным режимом редактирования, а старый сохранённый ключ удаляется при запуске. Метод `isOwner()` сохранён только для совместимости со старыми модулями; его результат **никогда нельзя** использовать как доказательство прав владельца для API или Firestore Security Rules. Старый ключ считается раскрытым — смена только в клиентском коде ничего не защитит.

Firebase и облачная идентификация разделены на три режима:

- `SyncModule` выполняет только чтение опубликованных данных; автоматическая запись, обновление и удаление отключены.
- `AuthService` включает только локальное редактирование в текущем браузере. Это **не** Google-вход и не серверная авторизация.
- `FirebaseIdentityModule` поддерживает отдельный ручной перенос личных проектов после Google-входа: предпросмотр, обязательное скачивание резервной копии, повторная проверка облака, явное подтверждение и создание только отсутствующих документов. Пакетная операция ограничена 20 проектами; существующие облачные документы не перезаписываются. Это не автоматическая синхронизация.

**Важное расхождение конфигурации:** клиентский флаг `FirebaseService._privateProjectCreatesEnabled` сейчас включён, но активный в репозитории `firebase.json` указывает на `firestore.rules`, где все клиентские записи запрещены. `firestore.create-only.rules` содержит прототип create-only правил, но не подключён к `firebase.json`. Поэтому клиентский интерфейс может предлагать перенос, однако сервер вправе отклонить запись; деплой текущего `firestore.rules` гарантированно оставит запись закрытой. Состояние правил в Firebase Console отдельно не проверено и не должно выводиться из CI.

До объявления ручного облачного переноса готовым необходимо согласовать целевую политику, проверить production Firestore Rules и Authorized Domains, прогнать соответствующие правила в Emulator и выполнить контролируемую проверку одной тестовой записи. Не включать автоматическую синхронизацию, обновление или удаление в рамках 1.0.

## Стандарты репозитория

- Файлы проекта используют UTF-8 и LF; правила редактора собраны в корневом `.editorconfig`.
- Структура каталогов отражает назначение кода: `core`, `modules`, `services`, `ui`, `utils`.
- Комментарии должны объяснять нетривиальное решение или ограничение, а не повторять очевидный код.
- Не оставлять персональные подписи генераторов, временные заметки и неактуальные TODO в production-скриптах.
- Удалять Git-ветки только после проверки, что их изменения уже находятся в `main` или заменены другой реализацией.

## Публикация

GitHub Pages публикует корень ветки `main`. Пути в `sw.js` относительные, потому что проект живёт по адресу `/DevSpace/`, а не в корне домена. При изменении статических ресурсов повышайте `CACHE_VERSION`.
