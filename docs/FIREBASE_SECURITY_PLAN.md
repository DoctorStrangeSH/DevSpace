# DevSpace — безопасная облачная синхронизация

Актуальный статус на 21.11.2026. Этот документ описывает **код в `main` и конфигурацию репозитория**, а не предполагаемое состояние Firebase Console.

## Краткий статус

- Локальные проекты, задачи и заметки сохраняются в браузере через `StorageService`.
- `AuthService` включает локальный режим редактирования; это не аутентификация и не доказательство прав владельца.
- `FirebaseIdentityModule` использует отдельный Google Authentication flow.
- `SyncModule` выполняет только чтение; автоматическая запись, обновление и удаление проектов отключены.
- Ручной перенос в личную коллекцию реализован в клиенте: обязательный backup, preview, повторное чтение облака, сверка UID и проекта, явное подтверждение, транзакционное создание отсутствующего документа и повторная проверка результата. Пакетный перенос ограничен 20 проектами.
- Клиентский флаг `FirebaseService._privateProjectCreatesEnabled` сейчас равен `true`.
- **Активные правила репозитория всё ещё read-only:** `firebase.json` указывает на `firestore.rules`, где `allow write: if false`. Поэтому при деплое правил из репозитория ручная запись будет запрещена.
- `firestore.create-only.rules` — тестируемый прототип create-only политики, но он не подключён к `firebase.json`.
- Production rules в Firebase Console этим репозиторием не проверяются. Не считать ручную облачную запись доступной или проверенной только по включённому клиентскому флагу.

## Два независимых механизма доступа

### Локальное редактирование

`AuthService.login()` включает локальные правки на этом устройстве. Данные сохраняются в `localStorage`. Режим не создаёт Firebase session и не должен использоваться для доступа к API, Firestore или другим серверным ресурсам.

### Google Identity и ручной перенос

`FirebaseIdentityModule` отдельно выполняет Google sign-in. Для загрузки проекта проверяются активный UID, успешный backup, результат свежего предпросмотра, отсутствие конфликтующего ID и неизменность локального содержимого. `FirebaseService.createPrivateProjectIfAbsent()` использует транзакцию: существующий документ не перезаписывается; после создания выполняется чтение и сверка payload. Выход из аккаунта или смена UID отменяет незавершённые операции.

Эта операция — **ручной перенос**, а не синхронизация: она не обновляет и не удаляет существующие облачные проекты, не запускается автоматически и не делает локальные изменения облачными.

## Активные Firestore rules

Файл `firestore.rules`, подключённый в `firebase.json`, разрешает чтение только `users/{uid}/projects/{projectId}` владельцу по UID и запрещает все записи. Старые коллекции и остальные пути закрыты.

CI job `Firestore rules emulator` проверяет именно этот файл в тестовом проекте `demo-devspace-rules`. Успешный CI подтверждает read-only политику репозитория; он **не** подтверждает состояние production Rules в Firebase Console.

## Create-only prototype

Файл `firestore.create-only.rules` содержит прототип, который разрешает владельцу только создание документа с точным набором полей `id`, `schemaVersion`, `payload`, `updatedAt`; update/delete запрещены. Для него существует отдельный тестовый файл `tests/firestore.create-only.rules.test.cjs`, однако прототип не подключён к `firebase.json` и не является активной политикой проекта.

Не публиковать этот файл автоматически. Сначала согласовать переход, проверить правила в Emulator, сохранить текущие production rules и подтвердить, что схема совпадает с клиентской реализацией.

## Перед признанием облачного переноса готовым

1. Открыть Firebase Console проекта `devspace-aa564` и проверить фактически опубликованные Firestore Rules.
2. Проверить, что `doctorstrangesh.github.io` находится в Authorized domains Firebase Authentication.
3. Сверить production rules с выбранной политикой и файлами репозитория.
4. Если владелец согласует create-only перенос — подключить проверенные правила, прогнать Emulator и получить зелёный CI.
5. Скачать локальный backup.
6. Выполнить одну контролируемую загрузку тестового проекта под правильным Google UID.
7. Повторно прочитать документ, проверить payload и подтвердить, что существующие документы не меняются.
8. Отдельно проверить отказ чужому UID, update и delete.

До выполнения этих шагов ручной облачный перенос считать **неподтверждённым**. Локальный режим и локальный JSON backup продолжают работать независимо от Firebase.

## Безопасность и ограничения

- Не хранить Firebase/Google access tokens в обычном `localStorage`.
- Не считать email, локальный edit-mode или клиентский флаг авторизацией.
- Не рендерить поле `payload` как доверенный HTML.
- Не включать автоматические массовые update/delete.
- Ошибки облака не должны изменять локальные проекты.
- CI Emulator не заменяет аудит фактически опубликованных production rules.
